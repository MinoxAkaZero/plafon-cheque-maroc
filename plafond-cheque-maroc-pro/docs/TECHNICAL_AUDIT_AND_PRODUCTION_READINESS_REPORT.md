# PlafondChèque Maroc Pro (v11.0.0) — Full Technical Audit, Security Architecture, Release-Readiness & User-Data Migration Report

## Executive Technical Assessment

The **PlafondChèque Maroc Pro** codebase has undergone a comprehensive line-by-line architectural, cryptographic, persistence, business-logic, notification, and mobile release engineering audit. The inspection covered the standalone ES modules (`src/engine/calendar.mjs`, `src/engine/distribution.mjs`, `src/engine/words.mjs`, `src/security/crypto.mjs`, `src/notifications/notifier.mjs`, and the newly introduced `src/persistence/storage.mjs`), the unified Progressive Web Application entrypoints (`index.html`, `public/index.html`, `gestion_cheques_maroc.html`, `public/gestion_cheques_maroc.html`), the offline Service Worker (`sw.js` and `public/sw.js`), the Capacitor native configuration (`capacitor.config.json`, `android/app/src/main/AndroidManifest.xml`, `ios/App/App/Info.plist`, `ios/App/App/PrivacyInfo.xcprivacy`), the GitHub Actions CI/CD pipelines (`.github/workflows/build-ios-and-android.yml` and `.github/workflows/main.yml`), and the automated verification suites (`tests/engine.test.mjs` and `tests/e2e_browser_audit.py`).

Seventeen concrete software defects, cryptographic weaknesses, data-persistence race conditions, business-rule divergences, and CI/CD configuration hazards (`BUG-01` through `BUG-17`) were identified, reproduced, and resolved in the source code. Every modification preserves existing functionality, Moroccan banking rules, trilingual support (`fr`, `ar` RTL, `en`), and backward compatibility with historical backups while elevating the application to a verifiable `v11.0.0` engineering baseline.

### 2. Cryptographic & Key-Management Architecture (Section 2 Audit)

#### 2.1 Removal of Non-Standard Fallback Cryptography and Iteration Downgrades
During the security inspection of the inline application script, two critical issues were confirmed:
1. A fallback stream cipher (`aeadEncryptFallback` / `aeadDecryptFallback`) constructed from `HMAC-SHA256` in counter mode was invoked whenever `window.crypto.subtle` was undefined, yet its output envelope still declared `"cipher": "AES-256-GCM"`.
2. The accompanying fallback key derivation function (`pbkdf2Sha256Fallback`) silently clamped the iteration count via `Math.min(iterations, 25000)` while recording `"iterations": 210000` in the metadata.

In `v11.0.0`, both fallback routines have been completely eradicated from the application codebase. All symmetric encryption and key derivation operations in `src/security/crypto.mjs` and `index.html` now exclusively invoke the W3C [Web Cryptography API Level 2](https://www.w3.org/TR/webcrypto-2/) (`SubtleCrypto`):
- **Authenticated Encryption**: Genuine `AES-256-GCM` ([NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final)) with a 256-bit key, a fresh 96-bit (12-byte) cryptographically random initialization vector (`window.crypto.getRandomValues(new Uint8Array(12))`) generated per encryption operation, and a 128-bit authentication tag.
- **Password-Based Key Derivation**: Genuine `PBKDF2-HMAC-SHA256` ([NIST SP 800-132](https://csrc.nist.gov/pubs/sp/800/132/final)) with a 128-bit (16-byte) CSPRNG salt and a unified default work factor of **`210,000` iterations** across both `src/security/crypto.mjs` and the browser application, aligning with [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) guidance while maintaining smooth responsiveness on mid-range mobile devices.
- **Fail-Safe Behavior**: If `window.crypto.subtle` is unavailable (for example, if a user opens the HTML over an untrusted plain-HTTP origin where the browser disables `SubtleCrypto`), `assertWebCryptoAvailable()` refuses to downgrade, blocks unencrypted or custom-cipher writes, and displays a prominent red security alert banner (`#storagePersistenceWarningBanner`) explaining that `HTTPS`, `localhost`, or the native Android/iOS application is required.
- **Metadata Validation & DoS Protection**: Before any decryption or key unwrapping is attempted, `validateEncryptionEnvelope()` verifies that `cipher === 'AES-256-GCM'`, `kdf === 'PBKDF2-SHA256'`, `iterations` is an integer bounded within `[10,000, 2,000,000]` (preventing CPU exhaustion from maliciously crafted backup files with `iterations: 999999999`), `salt` is a valid 128-to-512-bit hexadecimal string, and `iv` is an exact 96-bit (24-hex-character) string.
- **Case-Sensitivity Preservation with Legacy Fallback**: Previously, `deriveKekFromSecret` and `derivePinPBKDF2Browser` called `.toUpperCase()` on the user's secret, reducing the entropy of alphanumeric passphrases. In `v11.0.0`, new PINs and alphanumeric passphrases preserve exact case sensitivity (`Atlas#2026` $\neq$ `atlas#2026`). When verifying an existing hash or unwrapping a legacy DEK, if the exact-case check fails and the input contains lowercase letters, the verifier automatically tests the uppercase-normalized derivation so no existing user is locked out during upgrade.

#### 2.2 Tiered Key-Management Architecture at Rest
To address the vulnerability where an unwrapped device DEK was stored in `localStorage` (`pcm_device_dek_v3`) alongside the encrypted database when no PIN was configured, `v11.0.0` implements a three-tier key hierarchy:
1. **Tier 1 — Native Hardware-Backed Storage (Android Keystore & iOS Keychain)**: When running inside the Capacitor mobile shell with `SecureStoragePlugin` available, the 256-bit master DEK is stored inside the Android Hardware Keystore / iOS Keychain (`pcm_native_master_dek_v4`), completely separate from `IndexedDB` and WebView storage.
2. **Tier 2 — PIN / Passphrase Envelope Wrapping (All Platforms when PIN is Enabled)**: When the user configures a 4–8 digit PIN or 4–32 character alphanumeric passphrase, the 256-bit DEK is encrypted (`wrapDekWithSecret`) under two independent `AES-256-GCM` Key Encryption Keys (KEKs) derived via `PBKDF2-HMAC-SHA256` (`210,000` iterations): one from the user's PIN/Passphrase (`wrappedDekByPin`) and one from the 12-character Recovery Key (`wrappedDekByRecovery`). All device keys (`device_non_extractable_crypto_key`, `device_unwrapped_dek`, and `pcm_device_dek_v3`) are immediately purged from `IndexedDB` and `localStorage`. When the application locks (`lockApplicationNow()`), `sessionVaultDekBytes`, `sessionVaultCryptoKey`, `photoMemoryCache`, and `state.operations` are wiped from RAM.
3. **Tier 3 — Non-Extractable Web Crypto `CryptoKey` (Web/PWA without PIN)**: On Web/PWA when the user has not yet enabled a PIN, `ensureSessionVaultDek()` generates (or migrates any legacy `pcm_device_dek_v3` into) a W3C Web Crypto `CryptoKey` with **`extractable: false`** and stores that `CryptoKey` object in `IndexedDB` (`IDB_KEY_STORE` key `device_non_extractable_crypto_key`), deleting `pcm_device_dek_v3` from `localStorage`. Because `extractable` is `false`, `window.crypto.subtle.exportKey()` is permanently forbidden by the browser's C++ Web Crypto engine. The Security Settings panel clearly explains that on Web/PWA without a PIN, local browser access on an unlocked computer can still use the non-extractable key within the same origin, and recommends enabling a PIN/Passphrase for full offline at-rest protection.

### 3. Database Persistence, Conflict Resolution & Binary Photo Blobs (Section 3 Audit)

1. **Single Authoritative Source of Truth with Revision Reconciliation**:
   - `IndexedDB` (`PlafondChequeMarocDB`, schema version `4`) is the authoritative primary database, containing three object stores: `app_state` (`main_profile` and `pre_restore_rollback`), `vault_keys` (`device_non_extractable_crypto_key`), and `cheque_photos_blobs` (encrypted binary photo `Blob` records).
   - Every call to `saveState()` increments a monotonic integer `state.revision` and updates `state.updatedAt` (ISO-8601 UTC timestamp), writing the identical encrypted envelope to `IndexedDB` and mirroring it to `localStorage` (`plafond_cheque_maroc_v2`).
   - On startup, `loadState()` reads both `IndexedDB` and `localStorage` and invokes `selectAuthoritativeStateSnapshot(idbLoaded, lsLoaded)`. If an interrupted write left `localStorage` with a higher `revision` or newer `updatedAt` than `IndexedDB` (or vice versa), the newer valid record is selected and immediately synchronized back to the lagging store.
2. **Elimination of Silent In-Memory Fallback**:
   - The previous `createMemoryIdbShim()` has been removed. If `IndexedDB` is blocked or fails, `saveState()` falls back to encrypted `localStorage` (`state.persistenceStatus = 'DEGRADED_LOCALSTORAGE_ONLY'`) and displays an amber warning banner notifying the user that photo storage is constrained and advising regular JSON backups. If both `IndexedDB` and `localStorage` fail (`state.persistenceStatus = 'UNAVAILABLE_VOLATILE'`), `saveState()` returns `false` and displays a high-visibility red alert banner warning the user that browser storage is blocked and changes must be exported before closing the window.
3. **Encrypted Binary `Blob` Photo Storage & Orphan Garbage Collection**:
   - Attached cheque photographs are resized and compressed via `compressAndResizeChequeImage(dataUrl, 1280, 600, 0.72)` (maintaining sharp legibility of Moroccan cheque numbers, courtesy/legal amounts, dates, and signatures at `~12–85 KB` per cheque), encrypted as binary `Uint8Array` payloads with `AES-256-GCM`, and stored as native `Blob` instances in `cheque_photos_blobs`.
   - Deleting an operation (`delete_op`), deleting the last cheque of an operation (`delete_cheque`), clearing a draft photo, or resetting the database now invokes `deletePhotoBlobFromIndexedDB(photoId)` and `garbageCollectOrphanedPhotoBlobs()`, ensuring zero orphaned binary blobs accumulate in `IndexedDB`.

## Part III — User-Data Migration Guide (Deliverable E)

### 1. Automatic In-Place Upgrade (Existing Web, PWA, Android & iOS Users)
Existing users upgrading from any previous version (`v1.0` through `v10.2`) to **`v11.0.0`** require **zero manual intervention**:
1. **Automatic Conflict-Free State Loading**: On first launch of `v11.0.0`, `loadState()` inspects both `IndexedDB` (`PlafondChequeMarocDB`) and `localStorage` (`plafond_cheque_maroc_v2` and legacy `plafond_cheque_maroc_v1`), selecting the most recent snapshot via `selectAuthoritativeStateSnapshot()`.
2. **Seamless Encryption-at-Rest Migration**:
   - If the user's database was stored in legacy plaintext JSON (`loaded.operations` array without `encryptedVault`), `loadState()` automatically preserves `companyName`, `plafondJournalier`, `holidays`, `notificationSettings`, `language`, `lwalidMode`, and all `operations`/`tranches`, generates a non-extractable 256-bit `AES-256-GCM` `CryptoKey` in `IndexedDB`, moves embedded cheque photos into encrypted binary `Blob` records in `cheque_photos_blobs`, and encrypts the financial vault at rest.
   - If the user had a legacy `pcm_device_dek_v3` hex key in `localStorage`, `ensureSessionVaultDek()` imports that exact key into a non-extractable `CryptoKey` (`extractable: false`) in `IndexedDB`, decrypts the existing vault without data loss, and deletes `pcm_device_dek_v3` from `localStorage`.
3. **PIN & Recovery Key Compatibility**:
   - Existing `PBKDF2-SHA256` PINs and Recovery Keys (whether created with `100,000` or `210,000` iterations, and whether uppercase-normalized or case-sensitive) continue to unlock the application and unwrap the vault DEK seamlessly.
   - If a very old pre-WebCrypto custom PIN hash is detected without a wrapped DEK, `loadState()` safely clears only the legacy weak PIN hash after migrating the user's operations so the user can configure a new `PBKDF2-SHA256` PIN in **Paramètres → Sécurité**.

### 2. Restoring Historical Backups (`v8.0`, `v9.0`, `v10.x`, and `v11.0`) & Using 1-Click Rollback
1. **Recommended Pre-Update Precaution**: Before installing a major update on a production device, users can optionally open **Paramètres → Sauvegarde & Restauration** and click **Télécharger Sauvegarde JSON** (or **Exporter Sauvegarde Chiffrée AES-256**).
2. **Full Backward Compatibility on Import**:
   - Unencrypted JSON backups from `v8.0+` (with or without `integrityHash`) and encrypted `.enc.json` backups (whether encrypted with `100,000` iterations in `v8.0–v9.0` or `210,000` iterations in `v10.0–v11.0`) are validated through the 7-step `validateAndPrepareBackupRestore()` pipeline.
   - Restoring a backup now restores **all** application data: `operations`, `tranches`, attached cheque photographs (`photoDataUrl` -> re-encrypted into `IndexedDB` `Blob` storage), `companyName` (synchronized with the A4 report header), `plafondJournalier`, `holidays`, `notificationSettings`, `language`, and `lwalidMode`.
3. **Automatic Pre-Restore Rollback Protection**:
   - Immediately before any backup import overwrites the current state, `v11.0.0` automatically saves a complete snapshot of the user's pre-import state under `id: 'pre_restore_rollback'` in `IndexedDB` (`PlafondChequeMarocDB`), ensuring that an accidental import never permanently destroys prior records.
